# 模板：《补充材料与信息确认清单》

用途：任何子技能的入口闸门（`route.py --gate`）判定缺项时，本轮**只出这份清单与提问**，不产出文书正文（铁律 4）。

本文件是给人看的清单视图，不是材料台账。唯一台账是案件目录的 `case.json`；`route.py --gate` 与 `verify_suite.py` 只读 `case.json`，不解析本文件。清单中的每一项都能在 `case.json` 的 `facts` 找到对应 key 与 status，手工勾选或改写本文件不会改变闸门结论。

## 一、清单视图（写入案件工作目录 `案件档案/00-材料补充清单.md`）

生成方式：

```bash
python3 <suite>/scripts/intake.py checklist --gate <子技能号> --profile <profile> --facts <案件目录>/case.json
```

取输出 JSON 的 `markdown` 字段作为视图正文；各项完整状态见同次输出的 `requirements[].record`。若本任务有 `gate_any_ids`，输出另含 `gate_any[]`，逐项给出 `id`／`label`／`record`，视图正文末尾以“以下任一项（gate_any_ids）”单列该组。

| `case.json` 状态 | 含义 | 闸门效果 |
|---|---|---|
| `confirmed` 且有 `value` 与 `evidence` | 已核事实 | 计入已提供 |
| `pending` 且有 `pending_id` 与 `question` | 已登记待确认 | 仅草案可用 |
| `conflict` | 材料互相冲突 | 草案与提交均阻断 |
| `unknown`（仅 `allow_unknown`）且 `follow_up` 完整 | 已登记补料行动 | 仅草案可用，提交仍阻断 |
| `not_applicable` 且有 `reason` | 已核为不适用 | 视为已核 |
| 其他或缺记录 | 未提供 | 阻断 |

视图示例：

```markdown
case: [[案件代号]]

- [x] 合同与仲裁条款全文（或扫描页可读文本）——confirmed
- [ ] 争议双方与相关第三方的主体名称、注册地、往来地址——pending Q2
- [ ] 争议事实时间线（含关键函件与日期）——unknown，follow-up 已登记
```

有任选其一闸门时，正文末尾追加：

```markdown
以下任一项（gate_any_ids）：
- [x] 机构官网链接（rules.official_url）
- [ ] 条款原文（rules.clause_text）
- [ ] data/official 已缓存文本（rules.cached_text）
```

规则：
1. 项目文字与 `suite.yaml` 该子技能的 gate 项对应，key 以 `gate_ids` 或 `gate_any_ids` 为准；不要为凑数拆出证据不存在的条目。
2. 一项只对应一个 fact key 和一份可交付材料，不要把三件事并成一个键。
3. "问过但用户没答"保持 `pending` 或 `unknown`，不得改成 `confirmed`；没有证据就不填 `value`（铁律 3）。
4. 状态只用上表枚举；本文件中的 `[x]` 只是显示，不能作为闸门输入，也不能替代 `case.json`。
5. `gate_any_ids` 是“任一项即可”的来源基础，不是并列必填；至少一项 `confirmed` 才满足，全部缺失时返回一条 `gate_any` 缺项。不得把没有证据的候选项勾成 confirmed 来绕过闸门。

## 二、发给用户的提问稿（中文，五段，不超过一屏）

```markdown
# [[案件代号]]｜[[文书名]] 起草前需要确认的事项

## 1. 为什么现在需要这些
[[一句话说明：本程序的哪一步由哪条规则触发；缺这些会导致什么后果（期限起算／机构退回／管辖失权）]]
（规则引用带来源标记；未取得官方文本前只写"以适用规则版本为准"）

## 2. 请提供（按优先级）
[[P0 阻塞项：缺即不能起草——逐条写"要什么、什么形式、从哪取、期限前"]]
[[P1 可先用占位起草——写明"暂以黄色高亮占位呈现，交付前必须替换"]]

## 3. 请确认以下理解是否正确
[[把本套件从材料中推出的事实做成陈述句，逐条请用户确认或纠正；每条注明出处（哪份文件第几页/哪封函件）]]

## 4. 我方推断的默认项（不确认即按此起草，且文书中以高亮占位保留）
[[推断值 + 推断依据 + 换成其他值的影响]]

## 5. 下一步与时间
[[收到后的动作与预计交付日；本轮不做什么]]
```

## 三、涉外范围专用五问（`--scope` 返回 `REVIEW_REQUIRED` / `UNKNOWN` 时用，替换上面第 2、3 节）

```markdown
1. 当事人主体：[[是否有一方为境外主体、境外注册或境外实际控制]]
2. 标的与履行：[[标的是否在境外、履行地是否在境外]]
3. 法律事实：[[合同订立/履行/违约事实发生在何法域]]
4. 仲裁地与准据法：[[条款约定的机构、仲裁地、语言与准据法]]
5. 执行地：[[预计需要承认与执行裁决的法域]]
```
五项全部为否或无法判断 → 本套件不适用（铁律 0），说明原因并建议改用国内诉讼/国内仲裁的专门工具，本轮结束。

## 四、常见失分点

- 清单写得像"资料汇总请求"，用户不知道每份材料要什么形式、由谁出、几号前给。
- 把缺项埋进文书正文的括号里，而不进台账——交付配对与核验（`verify_suite.py` 的 FILL）会失败。
- 用推断值填满文书再回头补材料，等于违反闸门不可跳铁律。
- 把这份视图当成台账手工勾选，或另建一份 Markdown 清单过闸——`case.json` 之外没有第二个闸门输入。
- 一次问 30 项。P0 控制在 5 项内，其余标注"可先以占位起草"。
- 忘记写"问过未答"的项，导致下一轮重复提问，用户体感倒退。
